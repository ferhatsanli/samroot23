## EZB6 alternate authorization-route inventory

The EZB6 ABL contains two distinct direct/tail call sites to the persistent transition `LinuxLoader:0x26020`:

1. `0xD4BAC` — dormant interactive confirmation. Its only recovered normal entry is already blocked by the unconditional-false `0xCA790` gate.
2. `0x9324` — boot-time reconciliation. It invokes `BLInitToken (0xD60F0)`, queries EM result-vector bit 3, then converts it to the transition state argument.

No third direct/tail reference exists in the fully decoded LinuxLoader executable sections. Therefore there is no other locally exposed LinuxLoader transition caller.

The companion EZB6 Odin UEFI app does implement a privileged Samsung EM-token channel. Its code and diagnostics include `BL_EM_CMD_INSTALL_TOKEN`, `BLWriteToken`, `Process_EMTOKEN`, `EM_CMD_REQ_TOKEN_ESS_V1`, and token issuer/device/validity/expiry/mode parsers. The application rejects invalid, used, expired, device-mismatched, and unsupported token modes; LinuxLoader retains matching EM-token parsing/mode-query and `BLWriteToken` paths. This is direct evidence of a Samsung-authorized service-token installation/processing mechanism, not merely an unrelated string.

However, the static data available here does **not** identify a token mode that means “consumer bootloader unlock,” nor an end-user request/issuance path. The only proven downstream relation is boot-time `BLInitToken → EM result bit 3 → 0x26020`. It is therefore unsafe to call the Odin EM-token facility a user unlock procedure or to use an arbitrary token/archive. The likely issuer must be Samsung-authorized because the code verifies token issuer/device/validity and signature-related failures, but that is an inference, not an authorization to obtain or install one.
